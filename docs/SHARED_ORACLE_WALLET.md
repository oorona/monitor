# One shared Oracle wallet

This is the current wallet contract for **Watchword, Rollcall, Muster and Monitor**. Fresh deployments use one Oracle wallet containing every managed account password. Per-application namespaces and per-account wallets are not supported.

## Ownership and configuration

Watchword initializes the wallet and is its only writer. All four applications mount the exact same `WALLET_HOST_PATH` directory at `/wallets`. Backends read it; only the Watchword executor has write access. `ORACLE_WALLET_ROOT=/wallets` is fixed for the consumers. An entry is selected by a globally unique lowercase alias, never by a project-specific directory.

The combined installer uses one `.env` in the Watchword checkout, generated by `deploy-suite.sh configure`. Runtime releases store its absolute path in `.configuration-path` and every Compose command uses `--env-file`.

## Stored credentials

Passwords are Oracle named secret entries keyed as `watchword.password.<alias>` in the same encrypted `ewallet.p12` and auto-login `cwallet.sso`. This permits multiple accounts for the same database, including Watchword administrative accounts, in one wallet. It does not use native SEPS external authentication, whose per-database credential selection does not support this required account layout. See [Oracle's SEPS guidance](https://docs.oracle.com/en/database/oracle/oracle-database/19/dbseg/managing-secure-external-password-store-password-credentials.html).

`entries.json` contains versioned nonsecret alias metadata: account, privilege, expected DBID, DB_UNIQUE_NAME, container, host, port and service. `tnsnames.ora` maps every alias to its endpoint. `sqlnet.ora` requires Oracle native encryption and integrity checks. Passwords are never copied into registry JSON, target records, `.env`, command arguments or logs.

Each isolated Oracle worker invokes the bundled Java reader using Oracle's `OracleWallet` and `OracleSecretStore` classes. The private reader pipe supplies a transient password to that worker's explicit username/password database connection. Consumer APIs do not return it. Watchword exposes a separate administrator reveal action requiring HTTPS, session/CSRF authorization and reauthentication; access and copy are audited without the value. The auto-login wallet authorizes local mounted readers; it is not a per-entry authorization boundary.

## One active shared snapshot

```text
wallet/
  current -> .generations/<uuid>
  .writer.lock
  .generations/<uuid>/
    ewallet.p12
    cwallet.sso
    entries.json
    tnsnames.ora
    sqlnet.ora
  .operations/<uuid>.json
```

Every published snapshot contains **all entries together**. Snapshot directories are versions of this single shared wallet, never wallets allocated to individual accounts or tools. Readers pin `current` once for a connection so password and network metadata come from the same snapshot. Private regular files, validated metadata and a confined relative pointer are required; unsafe paths or missing aliases fail closed.

## Fresh setup and adding accounts

Follow [INSTALLATION.md](INSTALLATION.md). The installer runs `wallet init` once, prompts for the new wallet encryption password and preserves it on repeat initialization. Oracle accounts must already exist with DBA-assigned grants and passwords.

`wallet add` accepts an alias, account, endpoint, expected identity and privilege. It prompts for the account password and existing shared wallet encryption password. It takes the global writer lock, clones the entire active wallet, appends the named entry, writes the complete metadata and verifies a fresh account/DBID/database/container login. Only successful verification publishes `current` with compare-and-swap and fsync. Failed verification preserves the old active wallet and retains pending encrypted state with a nonsecret journal for review. It does not change Oracle accounts or grants.

`wallet list` returns only entry metadata. `wallet inspect` verifies the selected existing entry's supplied expected identity. Aliases cannot be overwritten or reused for another database. Different apps may use the same ordinary-account alias for the same database. SYS/SYSTEM and privileged entries are reserved for Watchword; consumers also reject administrative session identities after login.

Rollcall and Muster's old per-application onboarding APIs and seed commands are disabled. Their Compose deployments have no wallet writer sidecar. Monitor selects its alias from the shared database registry. A target path outside the one configured root is rejected.

## Current capabilities

Shared initialization, append-only entry registration, password retrieval within isolated workers and consumer connection wiring are implemented. The installer checks storage/retrieval for two disposable entries without contacting an Oracle database. Each actual target still requires fresh identity and workload checks on the destination server.

Watchword implements approval-bound OCI rotation, encrypted replacement staging, fresh login verification, whole-wallet publication and explicit reconciliation without repeating password changes. Rollcall/Muster reconnect through authenticated target probes; Monitor supplies fresh authenticated MCP status. The executor encryption key and probe tokens stay in a private runtime volume separately from wallet files. Other writers must respect an unresolved rotation reservation. See Watchword's installation and implementation guides for qualified releases and activation. Registering an initial entry alone does not qualify a database or consumer. No existing-deployment migration is required by the fresh deployment procedure.

Keep this document, `shared_wallet.py`, `WalletSecret.java` and the shared registry contract identical across all four repositories. Watchword's `scripts/check-suite-contract.py` checks those copies.
